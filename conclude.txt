จากการตรวจสอบอย่างละเอียดทั้งในระดับ Source Code, ER Diagram (diagram.txt), เอกสารข้อกำหนด (fullreport-03-1.pdf),

"ระบบแจ้งซ่อมออนไลน์ชุดนี้ยังไม่ได้เชื่อมต่อและทำงานร่วมกับฐานข้อมูลจริงในการดำเนินงานหลัก (Write Operations ทั้งหมด) 
แม้จะมีการต่อสาย Connection ไปยัง Supabase สำเร็จ แต่โค้ด Backend/Service Layer เกือบทั้งหมดเป็นการจำลองข้อมูล (In-Memory Mock State) 
และในส่วนที่พยายามอ่านฐานข้อมูล (Read Operation) โค้ดจะเกิด Runtime Crash ทันทีเนื่องจาก Field/Relation Mapping ไม่ตรงกับ Database Schema 
ก่อนจะหลุดเข้าไปใน catch-block และตกกลับไปดึงข้อมูล Mock มาแสดงผลบนหน้าจอ ทำให้หน้าเว็บภายนอกดูเหมือนทำงานได้ปกติแต่เบื้องหลังไม่มีการบันทึกข้อมูลลงฐานข้อมูลจริงแต่อย่างใด"

========================================================================================

1.1 เทคโนโลยีที่ใช้
- Frontend: Next.js 16.4.0 (App Router), React 19.3.0, Tailwind CSS v4, Lucide React Icons
- Backend / API Layer: Next.js Route Handlers (`app/api/...`)
- ORM Layer: Prisma ORM v6.19.3 (`@prisma/client`)
- Database: PostgreSQL (Supabase Cloud - Region: ap-northeast-2)
- Architecture Style: Monolithic Next.js Fullstack (Serverless API + React Client Components)

1.2 สภาพการเชื่อมต่อฐานข้อมูล (Database Connection Analysis)
- Connection Pool & Driver: 
  - Transaction-mode Pooler (PgBouncer): พอร์ต 6543 (`DATABASE_URL`) สำหรับ Query ปกติ
  - Session-mode Direct Pooler: พอร์ต 5432 (`DIRECT_URL`) สำหรับ Schema Migration (`prisma db push`)
- การทดสอบการเชื่อมต่อจริง:
  - ดำเนินการรัน `npx prisma db push` สำเร็จ โครงสร้าง 18 ตารางถูกสร้างขึ้นจริงบน Supabase Cloud
  - ทดสอบรันคำสั่ง Prisma ผ่าน Node.js สามารถเชื่อมต่อ ตรวจนับแถว และส่ง Query ไปยังตารางจริงได้
- ข้อเท็จจริงที่ตรวจพบ:
  1. ตัวแปรสภาพแวดล้อม `USE_MOCK_DATA="false"` มีผลเฉพาะจุดที่มีเงื่อนไขเช็ค แต่ในโค้ดส่วนเขียนข้อมูล (Create/Update/Delete) ไม่มีคำสั่ง Prisma บันทึกลงฐานข้อมูลเลย
  2. โค้ด Service Layer ทั้งระบบยังอิงอยู่กับตัวแปร Array ในหน่วยความจำ ได้แก่ `ticketsState`, `sparePartsState`, `requisitionsState`, `auditLogsState` ซึ่งข้อมูลจะหายไปทันทีเมื่อเซิร์ฟเวอร์ Restart

[ISSUE-01] ระดับความรุนแรง: CRITICAL
หัวข้อ: ฟังก์ชันการบันทึกข้อมูล (Write / Mutation) ทั้งหมดไม่เคยบันทึกลงฐานข้อมูลจริง

  2. `services/sparePartService.ts` บรรทัดที่ 47-87 (`createRequisition`), 92-110 (`approveRequisition`)
  3. `services/auditService.ts` บรรทัดที่ 28-36 (`logAction`)
- รายละเอียด:
  ในฟังก์ชันที่มีการเปลี่ยนแปลงข้อมูล (C-U-D) โค้ดทั้งหมดใช้คำสั่ง Array Mutation ใน JavaScript เช่น `ticketsState.unshift(newTicket)`, `requisitionsState.unshift(...)`, `ticket.status = ...` โดยไม่มีการเรียกใช้งาน Prisma Client เลยแม้แต่บรรทัดเดียว
- หลักฐานยืนยัน (Evidence):
  ทำการทดสอบเพิ่ม Ticket ใหม่ผ่านหน้าเว็บหรือยิง POST ไปที่ `/api/tickets` จากนั้นตรวจสอบจำนวนแถวในฐานข้อมูล Supabase โดยตรงด้วยคำสั่ง `SELECT COUNT(*) FROM tickets;` ผลลัพธ์ที่ได้คือ `0` แถว ข้อมูลที่เพิ่มขึ้นจะคงอยู่เฉพาะในแรมของ Process และเมื่อ Node.js Restart ข้อมูลจะสูญหายทันที

[ISSUE-02] ระดับความรุนแรง: CRITICAL
หัวข้อ: ฟังก์ชันการอ่านข้อมูล (Read Operation) พังขณะ Mapping ข้อมูลจาก DB จริง และ Fallback ซ่อน Error
----------------------------------------------------------------------------------------
- ตำแหน่งไฟล์ที่พบ:
  `services/ticketService.ts` บรรทัดที่ 20-111
- รายละเอียด:
  ในฟังก์ชัน `getTickets()` มีการเรียก `prisma.ticket.findMany(...)` แต่เมื่อได้ผลลัพธ์จาก DB กลับมา โค้ดพยายามเข้าถึง Properties ที่ไม่มีอยู่จริงใน Schema:
  - บรรทัดที่ 62: พยายามเข้าถึง `t.location.id` แต่ในตาราง `tickets` ไม่มี Relation `location` (มีเฉพาะ `equipment.location` และ `equipment` สามารถเป็น NULL ได้)
  - บรรทัดที่ 41: พยายามเข้าถึง `t.ticketNumber` แต่ใน Schema คอลัมน์คือ `id`
  - บรรทัดที่ 51: พยายามเข้าถึง `t.assignedTech` แต่ในตาราง `tickets` ไม่มีคอลัมน์หรือความสัมพันธ์มอบหมายช่าง
- หลักฐานยืนยัน (Evidence - จากการรันคำสั่งทดสอบจริงบน Node.js):
  จำลองการสร้างข้อมูลลงในตาราง `tickets` จริง 1 แถวแล้วรันโค้ด Mapping บรรทัดที่ 62 พบ Runtime Exception ทันที:
  `TypeError: Cannot read properties of undefined (reading 'id')`
  ส่งผลให้โค้ดหลุดไปเข้า `catch (err)` ที่บรรทัด 108:
  `console.warn('Prisma query failed, falling back to mock state:', err)`
  แล้วคืนค่า Array จำลองเดิมกลับไป ทำให้ระบบไม่สามารถแสดงข้อมูลจริงจาก DB ได้เลย

[ISSUE-03] ระดับความรุนแรง: HIGH
หัวข้อ: ความไม่สอดคล้องระหว่าง ER Diagram (diagram.txt) กับ Requirement และ Business Rules
----------------------------------------------------------------------------------------
- ตำแหน่งไฟล์ที่พบ:
  `diagram.txt` และ `prisma/schema.prisma`
- รายละเอียดข้อผิดพลาดเชิงโครงสร้าง:
  1. ขาด Foreign Key สำหรับช่างผู้รับผิดชอบงานบนตาราง `tickets`:
     - ใน Business Rules (BR4, BR5, BR6) และเอกสารหน้า 4 กำหนดให้มีการ "มอบหมายงานให้ทีมช่าง" และแสดง "ชื่อช่างผู้รับผิดชอบ"
     - แต่ใน ER Diagram (`diagram.txt`) ตาราง `ใบแจ้งซ่อม (Ticket)` มีความสัมพันธ์กับผู้ใช้เพียงแค่ `ผู้แจ้ง (reporterUserId)` และ `ผู้เปลี่ยนสถานะ (changedByUserId)` ในประวัติเท่านั้น ไม่มี FK ชี้ไปยังช่างที่ถูก Assign
  2. ขาด Foreign Key สถานที่ (`location_id`) บนตาราง `tickets`:
     - ใน ER Diagram ตาราง `tickets` เชื่อมไปยัง `equipments` เท่านั้น และ `equipments` ถึงจะเชื่อมไปยัง `locations`
     - แต่ในการใช้งานจริงตาม BR2 ผู้ใช้อาจแจ้งซ่อมความเสียหายของสถานที่ เช่น แอร์รั่ว หลอดไฟดับ ผนังชำรุด ซึ่งไม่มีรหัสครุภัณฑ์ หาก `equipment_id` เป็น NULL จะไม่สามารถระบุสถานที่ของใบแจ้งซ่อมได้
  3. ขาดคอลัมน์สำคัญที่หน้าเว็บและ BR ใช้งาน:
     - `ticket_number` (เช่น REQ-202505-0038 ตาม BR3)
     - `urgency` (ระดับความเร่งด่วน เช่น Critical, Urgent, Normal)
     - `admin_notes` และ `repair_notes`
     - `target_sla_date` และ `completed_at`

หัวข้อ: ความปลอดภัย (Security) - ไร้ระบบยืนยันตัวตน (No Auth) และไม่มีการตรวจสอบสิทธิ์ (Broken Access Control)
----------------------------------------------------------------------------------------
- ตำแหน่งไฟล์ที่พบ:
  `app/api/tickets/[id]/route.ts`, `app/api/tickets/route.ts`, `app/api/spare-parts/requisitions/route.ts`
- รายละเอียด:
  1. ไม่มีระบบ Authentication: ไม่มี Session, Token, JWT หรือการตรวจสอบคุกกี้ ทุก Endpoint อนุญาตให้ใครก็ได้ที่มี URL เข้าถึงได้ทันที
  2. Insecure Direct Object References (IDOR): บุคคลภายนอกสามารถส่งคำขอ `PATCH /api/tickets/{any_id}` พร้อมระบุ `action: "CANCEL"` หรือ `"CLOSE"` เพื่อสั่งปิดหรือยกเลิกคำร้องของคนอื่นได้โดยไม่มีการตรวจสอบว่าเป็นผู้แจ้งหรือช่างเจ้าของงานหรือไม่
  3. สิทธิ์ตามบทบาท (RBAC) เป็นเพียง UI Display: สิทธิ์ผู้ใช้ (`REPORTER`, `ADMIN_DISPATCH`, `TECHNICIAN`, `EXECUTIVE`) ถูกกำหนดผ่าน Dropdown หรือ URL Switcher บน Navbar หน้าบ้านเท่านั้น ไม่มี Middleware หรือ API-level Guard ป้องกัน

7. ข้อเสนอแนะในการแก้ไขและปรับปรุง (Prioritized Remediation Roadmap)
========================================================================================

ลำดับที่ 1 (ความสำคัญเร่งด่วนที่สุด - Urgent Database & ORM Alignment):
1.1 อัปเดต `prisma/schema.prisma` ให้สอดรับกับการใช้งานจริง:
   - เพิ่ม Relation ไปยังสถานที่โดยตรง: `locationId String?` และ `location Location?` บนตาราง `Ticket`
   - เพิ่ม Relation ไปยังช่างที่รับมอบหมาย: `assignedTechnicianId String?` และ `assignedTechnician User?` บนตาราง `Ticket`
   - เพิ่มฟิลด์ที่จำเป็นต่อระบบ: `ticketNumber String @unique`, `urgency String @default("NORMAL")`, `repairNotes String?`, `adminNotes String?`, `completedAt DateTime?`
1.2 รัน `npx prisma db push` เพื่อปรับโครงสร้างบน Supabase ให้ตรงกัน

ลำดับที่ 2 (เชื่อมต่อ Service Layer เข้ากับ Prisma อย่างสมบูรณ์):
2.1 แก้ไข `services/ticketService.ts`:
   - ใน `createTicket`: ใช้ `prisma.ticket.create(...)` ภายใน `$transaction` เพื่อบันทึกทั้งใบแจ้งซ่อม รูปภาพ (`ticket_attachments`) และประวัติสถานะแรก (`ticket_status_histories`)
   - ใน `assignTicket`, `acceptTicket`, `closeTicket`, `cancelTicket`: ใช้ `prisma.ticket.update(...)` ร่วมกับ `prisma.ticketStatusHistory.create(...)`
   - ใน `getTickets`: ปรับการอ่านและการ Map ข้อมูลให้ตรงกับ Schema จริง ปลดการ Fallback ไปหา Mock เพื่อให้เห็นปัญหาที่แท้จริง
2.2 แก้ไข `services/sparePartService.ts`:
   - ใน `createRequisition`: ใช้ `prisma.sparePartRequisition.create(...)`
   - ใน `approveRequisition`: ใช้ `prisma.$transaction` เพื่อปรับสถานะใบเบิก และสั่งหักลบจำนวนอะไหล่ใน `prisma.sparePartInventory.update({ data: { stockQuantity: { decrement: qty } } })`

ลำดับที่ 3 (แก้ไข Frontend Components ไม่ให้ฮาร์ดโค้ด):
3.1 แก้ไข `ActiveTicketTracker.tsx`, `CloseJobCard.tsx`, `EvaluationCard.tsx` ให้รับ `ticketId` จาก Dynamic Context หรือ Props แทนการระบุรหัสคงที่
3.2 เชื่อมปุ่มยกเลิกคำร้องของ `ActiveTicketTracker.tsx` เข้ากับ API `PATCH /api/tickets/${id}` จริง

ลำดับที่ 4 (ระบบความปลอดภัยและการจัดการไฟล์):
4.1 ติดตั้งระบบ Authentication (เช่น NextAuth.js / Supabase Auth หรือ Session Guard) เพื่อบังคับให้ล็อกอินด้วยอีเมล KKU ตาม BR1
4.2 กำหนด Role-based Access Control (RBAC) เพื่อป้องกันไม่ให้นักศึกษาทั่วไปสามารถกดยกเลิก ปิดงาน หรืออนุมัติการเบิกอะไหล่ได้
4.3 สร้าง API Route สำหรับรับและอัปโหลดไฟล์รูปภาพจริงไปยัง Supabase Storage Bucket แทนการใส่ URL ภายนอก

8. รายการที่ยังตรวจสอบไม่ได้และข้อมูลที่ต้องขอเพิ่มเติม
========================================================================================
1. API Credentials / Secret Key สำหรับบริการภายนอก:
   - ระบบแจ้งเตือนทางอีเมล (SMTP / Resend API) ตามตาราง `email_notification_logs`
   - Supabase Storage Bucket Access Key สำหรับจัดเก็บรูปถ่ายความเสียหาย
2. สิทธิ์ในการปรับปรุง Schema:
   - จำเป็นต้องได้รับการยืนยันว่า อนุญาตให้ขยาย Schema ใน `prisma/schema.prisma` เพื่อเพิ่มคอลัมน์ `assigned_technician_id`, `location_id`, `ticket_number` ได้หรือไม่ หรือต้องรักษารูปแบบตาม `diagram.txt` ไว้แบบห้ามแตะต้อง (Strict Diagram Constraint)
3. ระบบ KKU Single Sign-On (SSO):
   - ขอข้อมูล OAuth Client ID / Endpoint ของระบบ KKU Authentication กลาง (หากมี) เพื่อนำมาเชื่อมต่อการยืนยันตัวตนตาม BR1 และ BR12
